/hexagonal-skill-builder

Why a skill's shape is its behaviour

Why the skill works the way it does. For commands, read the how-to.

A skill's shape is its behaviour

A model follows a skill to the letter, and reads it in layers. What each layer costs decides how the skill must be built.

  • The description is read always, to decide whether to fire. If it never says when, the skill fires at the wrong time or never: that is named.
  • The entry is read every time it fires. Each line in it is paid for on every call, so it routes rather than teaches: that is small.
  • Pages are read on demand. A pointer to a page that moved sends the model nowhere, and it carries on without saying so: that is resolves.
  • Scripts run as written. One nobody tests was only ever watched: that is tested.

Four rules, and the rest is judgement

A rule is kept only if a script can check it and a skill once failed because of it. An earlier version of this builder held twelve rules. Eight of them enforced a folder layout, cost dozens of rewrites, and are recorded catching nothing. They went.

What a script cannot see is written down instead, as eight guards with the story behind each one. A clean check says nothing about them. So the skill tells Claude to read them before writing a number, an output or an edit script.

Why "hexagonal"

Skills are laid out as hexagons: the entry routes, and the pages behind it each have one job. The layout, and why it holds, is hexagonal-architecture's. This skill keeps it a habit, not a rule: the layout rules an earlier version held caught nothing.

Every rule has a story

The skill's evidence.md holds one story per rule and guard: a real failure, and what it cost. The skill cites them as (why: E-03), and resolves makes sure each citation has its story. A rule nobody can explain is the first one to be relaxed. A rule with its story stays.

Why it reads, and never writes

The check only reports. It changes no file, needs only Node, and opens no connection. So it is safe to pre-approve, which the skill does for that one command. It can gate a commit or a CI job without a second tool. You can run it on a skill you have not decided to trust yet. Fixing is the author's job, or Claude's, with the finding's → as the instruction.

Why README.md and docs/ sit outside the skill

SKILL.md and the pages it links are instructions: Claude follows them. A page written to convince a person would be followed too. So the pages for people live beside the skill, and nothing Claude reads points at them.

/hexagonal-architecture

Why every dependency points inward

Why the skill works the way it does. To get something done, see the How-to guides.

The core changes for business reasons, the edges for technical ones

A price rule changes when the business does. A database driver changes when a vendor does. Pointing every dependency inward keeps the second kind of change at the edge.

The core owns its ports

A port is written in the core's words, for the core's need. An interface shaped like its first adapter only moves the coupling one file over.

Hexagonal, clean, onion: one rule

The names differ in how many rings they draw. The rule they share is the one the check holds.

A skill is a hexagon too

A skill's verbs are its use cases, its domain pages what stays true, its adapters the tools it touches. A domain page that links a tool's page leaks the same way an import does, so the check reads links too.

One contract, said once

Five skills in this plugin have ports. Each used to explain ports, bindings and drop-ins in its own words, and the words drifted. The contract now lives in this skill, and each ports page keeps only its own ports.

Every skill with ports links the one contract instead of restating it, so a fix lands once. The link is marked "if installed": a skill added alone keeps its own ports and works without the contract page.

/doc-compass

Why docs need a compass

Why the skill works the way it does. To get something done, see the How-to guides.

Every reader arrives with one need

Diataxis sorts documentation by what the reader is doing, not by topic. Two questions place any page: is the reader doing or understanding, and are they studying or at work?

A page that answers two needs makes both readers read past the half they did not come for. That is why the skill splits such pages rather than adding headings to them.

Docs rot by omission, not by mistake

The docs this skill was built from were written with care. They went stale for three reasons. A page was added and the index was not. A heading was renamed and its links were not. A decision was reversed and the old record still read as current. Each is something nobody did. The check looks for exactly these, because they are the ones a careful writer misses.

Why seven rules, and why these

Each rule stands for a failure seen in a real docs set. The skill writes each one up. You can read them in evidence.md. A rule nobody has paid for would pass on every project and prove nothing. A script cannot see some things, such as a tutorial with a fork in it or a number written from memory. These stay in guards.md as guidance until someone finds a way to check them.

Rewrite, never annotate

A page that carries "Updated in v3" callouts asks the reader to merge two versions in their head. The skill rewrites the page to say what is true now. It keeps history where readers look for it: the CHANGELOG for what changed, and decision records for why.

Gravestones instead of deletions

Deleting a cited page breaks every citation at once, often in places the docs cannot see, such as code comments. A gravestone costs one short page and keeps every pointer working, so it is the default whenever something cites the old path.

Why the docs live outside the skill

The skill folder is loaded by the model on every call. People read these pages. Keeping them apart means neither pays for the other's text. This is the same choice hexagonal-skill-builder makes.

/testing-trophy

Why the trophy is widest at integration

Why the skill works the way it does. To get something done, see the How-to guides.

A test earns trust by resembling real use

Users meet modules together, never one function alone. An integration test fails when they do. A unit test with its neighbours mocked keeps passing.

A mock of your own code tests the mock

Mocking a module the project owns removes the seam that breaks. Mocks stay at the edge. These are the network, the clock, a paid API.

The name is the failure message

A test titled by its behaviour says what broke when it fails. A test titled checkLimit says only where to start reading.

The project chooses its strategy

The skill is opt-in. doc-compass asks only that examples are run by some test. Which strategy writes those tests is the project's call.

/big-o-optimizer

Why it proves both

Why the skill works the way it does. To get something done, see the How-to guides.

Faster and wrong is a bug

The common way a complexity cut breaks code is quiet: a Set drops duplicates, a Map reorders, an object key turns 1 into "1". So the tests run before the rewrite and after it, and a test is written first when none reaches the code.

The worst term only

O(n²) to O(n) changes what a program can handle. A cached length does not. Fixing the worst term first, and stopping when no pattern pays, keeps the change small and readable.

Numbers are read, never guessed

The Big O is read from quoted lines. A timing is copied from the command that printed it, at two sizes so the growth shows. Without a bench, the hand-over says "not measured" rather than inventing a speed-up.

The method is language-agnostic

A nested membership test is O(n·m) in every language. A hash set fixes it in every language. What changes is the spelling and the traps. One trap is an object key that turns 1 into "1". Another is a Go map that iterates in random order. A third is a Python list that cannot be a dict key. So the patterns are written once, generically, and each language's spelling and traps live in a language adapter. Without one, the skill reads the standard library's documented costs instead.

Why adapters

Every project proves things its own way: unit tests, golden files, a profiler, a perf budget in CI. Ports keep the method fixed and let the project plug its tools in by dropping one file, without forking the skill.

/radical-simplify

Why the order is strict

Why the skill works the way it does. To get something done, see the How-to guides.

The cheapest step is the one that no longer exists

Speeding up a step still leaves it to build, test, explain and maintain. Removing it costs nothing afterwards. So the method asks whether something should exist before it asks how to make it better, and every later step works only on what survived.

Automating first locks the mess in

Automation is the most expensive step to undo: it turns today's process into code. Automate a step that should have been removed and the waste becomes permanent and invisible. That is why automation comes last, after the process has been questioned, cut, simplified, redesigned and sped up.

Simple is designed around intent

Most complexity mirrors how an organisation is built, one screen per team, one approval per department. The Simplify and Reimagine steps redraw the flow around what the user is trying to do. This is why the skill favours defaults, context and one primary action over options.

Why a fixed output

A model asked to "simplify" tends to polish what is there. A section per step makes each one visible, so you can see what was questioned and removed, not only the final design. The closing count is read from the original and the proposal, never estimated, so the claimed gain can be checked.

The output used to close on "obvious, effortless, exceptionally well designed". Those words carry no fact, and the words a skill asks for are the words its output carries. The count replaces them: it says how much simpler, and anyone can check it.

Why it proposes and does not edit

A redesign is a decision for a person. The skill writes it. Changing the code is a separate request once you agree.

/glance-first

Why the answer, then the numbers, then the picture

Why the skill works the way it does. To get something done, see the How-to guides.

The page is built in the order the eye moves: answer, figure, picture, words.

A reader decides in the first line whether to keep going

Most readers of a summary stop early. So the first line is the answer, not a lead-in, and everything after it is proof they may skip.

A figure says how much, faster than a sentence

"The build is faster" asks to be believed. "12 → 3 minutes" does not. The numbers sit right under the answer. The size of the change is the second thing seen. A digit is required in every value. A word like "many" cannot pass as a figure. An empty list must be written on purpose.

The eye goes to a picture before it reads

A diagram that marks NEW: lands faster than the sentence describing it. So each block draws its picture first, and the first block must have one. The line under it only says what the picture proves.

A script holds the limits, not good intentions

Word caps, the 200-word budget and the reading order drift when only a writer watches them. The check refuses a brief that breaks one and says the fix, so the minute is held every time.

/glance-audit

Why an audit keeps so little

Why the skill works the way it does. To get something done, see the How-to guides.

A reviewer is trusted for what they leave out: one critical point beats ten fair ones.

Many lenses, few findings

Seven lenses look everywhere so nothing is missed. Most find nothing. The three tests then drop the hunch, the point the source already answers, and the point a reviewer already made, credited instead of repeated.

One point leads

A list of equals makes the reader rank it. So every critical point is kept, and otherwise only the most severe. The rest is folded as can wait, never lost. Nothing is rated up to fill the page.

A quote the reader can place

A comment is pasted on a passage, so its quote must be that passage, word for word, and occur once. The check holds it against the source text, never the context, so a comment always has an anchor.

It judges; others render and post

The judgement is the skill's, the form is glance-first's, and posting is the reader's. Keeping those apart is what lets it read a pull request without ever touching it.

doc-compass audits a doc set's structure. glance-audit challenges what one source claims.

/plain-language

Why 80% of STE, and why three levels

Why the skill works the way it does. To get something done, see the How-to guides.

ASD-STE100 has two parts. The skill takes the first and leaves the second.

STE part What it is In the skill
Writing rules short sentences, active voice, one instruction each yes
Dictionary about 900 approved words, one meaning each no

Why not the dictionary

  • It has no software words. "Mock", "rebase" and "adapter" are not in it.
  • It exists only in English. No official French version exists.
  • STE allows the technical words of a project. Rule 4 keeps their one meaning instead.

Why not one percentage for every text

A maintenance manual is all procedure. A skill writes steps, reports and review comments. Each one needs a different strictness:

  • A step is followed with the hands. Strict rules make it safe.
  • A report is read to decide. It needs a reason, so it gets 25 words, the STE limit for a description.
  • A comment goes to a person. It may ask a question and be polite. Strict rules would make it rude.

Why the passive voice is a hint

A script cannot tell "The file was deleted" (passive) from "The file was red" (an adjective). A false finding that fails a build teaches people to ignore the check. So the check prints a hint and does not fail.

Why one skill, not a rule in each skill

The rules live in one place. Another skill names a level in one line. A change to a rule reaches every skill at once, and no skill copies the rules.

Why "plain language"

Most people know the phrase. It works in every language. ISO 24495-1 (2023) defines it. STE is its stricter form for technical manuals.

/skill-retro

Why fix the skills, and never live

Why the skill works the way it does. To get something done, see the How-to guides.

A skill gets cheaper and truer only when its friction is fixed where the next session reads it.

A fix made in the running checkout changes the rules mid-game

The session that hit the friction is still running on the old text. So each fix goes to its own branch and worktree, and lands only after a person merges it.

No evidence, no fix

A guessed cause produces a guessed fix. Every finding carries a quote, an error line or a count copied from a script, and one without is dropped.

Tokens are paid at three rates

A description is paid every session, an entry body every session that fires the skill, another page only when read. Text said twice is paid twice, so weight.mjs finds the repeats and the fix removes before it adds.

Skill fixes stack beside features, not inside them

A skill fix should wait for no feature, and no feature for a skill fix. Two parallel stacks keep them apart, which is why stack-base.mjs refuses a skill branch based on a feature branch.

Handoffs and deferred rows are opt-in

Not every session runs subagents or parks work, so the default reads only what every session has.

/usage-runway

Why the clock, not a token ceiling

Why the skill works the way it does. To get something done, see the How-to guides.

The meter answers from the clock, because the token ceiling spread elevenfold.

A rule nobody can follow is not a rule

Long work had always been told to check its credit before starting a unit it could not finish. There was nothing to check it with. So the check was skipped and a limit landed mid-plan. The meter is one command and one word, so the rule can be kept.

A ceiling that spread elevenfold is not one to park on

Nothing on disk publishes the account's limit. Ceilings derived from three past limit hits read 8.7M, 5.3M and about 804k, and one window burned 11.4M with no limit at all. So burn is printed for reading, and the verdict comes from the reset time, which is exact when a limit was hit.

The window is not "the last five hours"

The first version anchored the window at the oldest turn of the last five hours. It told a session with four hours left to park at once. A rolling window opens on the first turn after five idle hours and advances in whole windows from there.

A limit may land between units, never inside one

An estimate is what the work should take. The x 1.5 margin is what it takes when something goes wrong. Checking before every unit, with that margin, puts the limit at a boundary.

/stack-and-ship

Why one stack, merged up, never forced

Why the skill works the way it does. To get something done, see the How-to guides.

A change is shipped when a reviewer can merge it without asking a question.

A force-push erases what a reviewer read

Rebasing a stack rewrites every branch above the fix, and a force-push replaces commits a reviewer already commented on. Merging the lower branch up keeps them. The cost is a merge commit per branch, which a squash merge removes at the end. So stacking tools whose submit command force-pushes are used only for the calls that never push.

One step, one pull request

A reviewer reads one plan step at a time, and the next step does not wait for that review: it branches from the previous one. Small PRs merge bottom first, each one already read.

The method is the skill's, the facts are the project's

Branch names, the TDD sequence and the stack rules hold in any repository. The commands, the checks, the board ids and which lines a PR body must hold do not. They live in one project file, so a second project adopts the skill by writing that file, never by editing the steps.

A title says the value, not the action

fix(cart): totals round once tells a reviewer and the changelog what changed for a user. fix(cart): add round helper tells neither. The check refuses the shape, not the words: wording is the author's.
